Somewhere right now, a pipeline is failing and a language model is getting blamed for it.

The accusation rarely sticks. Swap in a stronger model and the pipeline usually fails the same way, just more expensively. Because the model was never the whole system. Around every model call sits the instructions you wrote, the examples you picked, the tools you offered, the order of the steps, the wiring between them. That setup has a name: the **harness**. Given a good enough harness, a capable model can do almost anything. Given a bad one, no model can save you.

So the real question isn't "which model?" It's: where does your harness actually *live*?

Look at your current project. The instruction is a string in one file. The examples are a list in another. The retry logic is a decorator someone wrote in a hurry. The pipeline's shape exists nowhere at all, except in your head, and it's leaving when you do. You can't diff any of it. You can't ask "what changed between the version that worked and the version that doesn't?" and get an answer.

## The map and the territory

Code that runs is territory. Real, effectful, and opaque: the only way to know what it does is to run it and watch.

DSRs is built on one bet: **every harness should also have a map**. A single page that shows every step, every instruction, every tool, every connection. And here's the part that matters, because you've been burned by stale diagrams before: in DSRs the map is generated *from* the territory, on every build. It cannot drift. It cannot lie.

The map is not the territory. Unless the map is generated from the territory.

This is what a DSRs program looks like when it's written down. No Rust yet, just the map:

```text
dsrs 1
program frontdesk

model fast = "openai:gpt-4o-mini"

sig Main {
  in  ticket: string
  out reply: string
}

// signatures trimmed for the teaser

main: Main = seq {
  triage  = predict Triage (ticket = $.ticket)
  drafter = cot Draft @fast (ticket = $.ticket, category = triage.category)
  out { reply = drafter.reply }
}
```

Two model calls, one feeding the other, and every knob in plain sight. That file is not documentation someone wrote about the program. That file *is* the program: you can run it, serve it, check it into git, and diff it against last Tuesday's version. You write ordinary Rust, and this falls out of the build.

## What a map buys you

Once your harness is a thing you can hold, doors start opening:

- **Diff it.** Two versions of a harness are two text files. The change that broke production is a line, not a vibe.
- **Replay it.** Every run is recorded. Re-run yesterday's traffic against today's harness without paying for the parts that didn't change.
- **Optimize it.** Every instruction and every example has a named address. An optimizer can lay candidate edits over your program like tracing paper, score them, and hand you the winner. Your code never changes.
- **Serve it.** `dsrs serve frontdesk.dsrs` and the map is an endpoint.
- **Let a model write one.** The text form is small on purpose. A harness that fits on a page is a harness an LM can generate, and the same checks that guard yours guard its.

Big claims. The rest of this book earns them one chapter at a time, by building a real thing: **Front Desk**, a support-ticket triage and reply service, grown from a single typed call into an optimized, replayable, served program.
