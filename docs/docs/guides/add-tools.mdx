A tool is a function the model may call while it works. You describe what the tool does; the model decides when to use it. DSRs has two kinds. Host tools are Rust functions in your binary. Sandboxed tools are small JavaScript snippets that travel inside a `.dsrs` program file.

## Goal

Write a tool, hand it to an agent, and control when the agent loop stops.

## Host tools

A host tool is a normal Rust function with a body. The body is the implementation. The doc comment is what the model reads when it decides whether to call the tool.

```rust
use dspy_rs::tool;

/// Uppercase text.
#[tool(caps("demo:shout"))]
fn shout(text: String) -> String {
    text.to_uppercase()
}
```

- `caps("...")` is optional. It names what the tool is allowed to touch (for example `net:search` or `fs:read`). A capability is just a label; the host checks these labels before it runs a program, so nothing gets network or file access silently.
- The function stays plain Rust. You can still call `shout("hi".to_string())` yourself in tests.

Tools can be async, and they can fail. A fallible tool returns `Result` with any error type that prints nicely:

```rust
/// Fetch a page and return its text.
#[tool(caps("net:http"))]
async fn fetch(url: String) -> Result<String, String> {
    // your implementation
}
```

## Give tools to an agent

An agent is a step that runs in a loop: the model thinks, calls tools, reads the results, and answers when it is done. List the tools with `tools(...)`:

```rust
use dspy_rs::agent;

/// Research the question. Use the shout tool when volume is needed.
#[agent(tools(shout), max_turns = 3, budget(tokens = 50_000, on_exhausted = finalize))]
fn research(question: String) -> String;
```

Useful options:

- `tools(a, b)` lists the tools the model may call.
- `max_turns = N` caps the number of loop rounds.
- `budget(tokens = N, calls = N, on_exhausted = finalize)` caps spending. `finalize` means "ask for a final answer instead of failing" when the budget runs out.
- `model = "@name"` pins the loop to a named model, same as any [step](/docs/guides/write-steps).

## Stop tools: ending the loop on purpose

Sometimes you want the model to end the loop by making one explicit call, instead of just writing a final message. Declare a tool whose inputs match the agent's output fields, and list it in `stop_tools(...)`:

```rust
/// Submit the final answer. Call this exactly once, when you are done.
#[tool]
fn submit(research: String) -> String {
    research
}

/// Research the question. Call submit when you have the answer.
#[agent(tools(shout, submit), stop_tools(submit), max_turns = 6)]
fn research(question: String) -> String;
```

When the model calls a stop tool, the loop ends right there. The arguments of that call become the step's output. The tool body does not run. That is why the stop tool's inputs should be named after the agent's outputs (`research` here).

## Sandboxed tools

A sandboxed tool is not Rust. It is a small piece of JavaScript stored inside the `.dsrs` text file itself. It runs in a safe sandbox, so it cannot reach the network or the disk unless the file declares a capability and the host allows it.

Sandboxed tools live in the program text, not in your Rust code. In a `.dsrs` file they look like this:

````
tool shout "Uppercase the text" {
  in  text: string
  out shout: string
} js```
(args) => ({ shout: args.text.toUpperCase() })
```
````

Because the code is inside the file, the program is fully portable: anyone who can run the file gets the tool too. Host tools are the opposite: the file only names them, and the binary that serves the program must supply the implementation.

For the full text format, see the [`.dsrs` file reference](/docs/reference/dsrs-file).

## Common mistakes

**Forgetting the body on a host tool.** `#[tool]` needs a real function with a body. A bodyless function is a step, not a tool.

**A stop tool with the wrong input names.** The stop tool's arguments become the agent's output. If the names do not match the agent's output fields, the output cannot be filled in.

**Skipping the doc comment.** The doc comment is the tool's description. It is the main thing the model uses to pick a tool, so write it for the model, not for other programmers.
