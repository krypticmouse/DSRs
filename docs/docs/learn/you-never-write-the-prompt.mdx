You shipped an app. Congratulations, by the way. It's called **Sourdough**, it tracks sourdough starters, and people love it in the way people only love software that touches something they feed by hand.

Then the update went out, and the first ticket arrived:

> "I updated last night and now my starter tracker shows 0 days. Did the update kill my starter data?? Herman is FOUR YEARS OLD."

By lunch there are forty of these. Some are bugs. Some are billing. Some are people asking how to export a CSV. Somebody needs to read every one, figure out what it is, and route it. That somebody is you, and you have a language model sitting right there.

So you know what happens next. You've done it before.

## The dance you already know

You open a file and write a prompt string. `"You are a helpful support agent. Classify the following ticket into one of: bug, billing, how-to, feature request. Return ONLY the category, no explanation."`

You know why that ONLY is capitalized. It's load-bearing. It's there because the model once answered `Sure! This looks like a bug report.` and your `match` statement fell over. So you parse. You lowercase, you trim, you strip a trailing period, you handle `"bug."` and `"Bug Report"` and that one time it answered in French. Then you tweak the prompt, and the parse breaks differently, and you tweak the parser, and now there are two of you: one negotiating with a model, one negotiating with a string.

Here's the uncomfortable question: what were you actually trying to say?

You were trying to say *ticket text goes in, one of four categories comes out*. That's it. That's a function signature. Everything else, the pleading capitals, the format bribes, the parser, is you hand-compiling a type into English and hand-parsing English back into a type.

DSRs takes that observation literally. You declare the contract. The machinery writes the prompt, calls the model, and parses the response back into your types. You never write the prompt.

## Set up

```bash
cargo add dspy-rs tokio anyhow
export OPENAI_API_KEY="sk-..."
```

## Say what you mean, in types

The four categories you were begging for in prose? That's an enum:

```rust
use dspy_rs::Schema;

#[Schema]
#[derive(Clone, Debug)]
enum Category {
    Bug,
    Billing,
    HowTo,
    FeatureRequest,
}
```

And the task itself, ticket in, category out, is a **signature**: a plain struct that declares one interaction with a model.

```rust
use dspy_rs::Signature;

/// Classify a support ticket for the Sourdough app.
#[derive(Signature, Clone, Debug)]
struct Triage {
    /// The full text of the customer's ticket
    #[input]
    ticket: String,

    #[output]
    category: Category,
}
```

Read it again, because everything in this book grows from this struct. The doc comment on the struct is the instruction the model receives. The `#[input]` field is what goes in. The `#[output]` field is what must come out, and its *type* is doing the talking: because `category` is a `Category`, the model is told exactly which four values exist, and the response is parsed back into a real Rust enum. Not a string you hope is an enum. A `Category`, or an error that says why.

A signature doesn't call anything. It's pure data, a contract. To execute the contract, hand it to a predictor:

```rust
use dspy_rs::{configure, init_tracing, LM, Predict};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    init_tracing()?;

    configure(
        LM::builder()
            .model("openai:gpt-4o-mini".to_string())
            .build()
            .await?,
    );

    let triage = Predict::<Triage>::new();

    let out = triage
        .call(TriageInput {
            ticket: "I updated last night and now my starter tracker shows 0 days. \
                     Did the update kill my starter data?? Herman is FOUR YEARS OLD."
                .into(),
        })
        .await?;

    println!("category: {:?}", out.category);
    Ok(())
}
```

```text
$ cargo run
category: Bug
```

That's the whole program. `TriageInput` was generated for you from the `#[input]` fields. `out.category` is a `Category::Bug`, ready for a `match`, no lowercasing in sight.

## Inventory of the things you didn't write

No prompt string. No "return ONLY". No schema paragraph explaining what the valid categories are, the enum *is* that paragraph now. No parser, no trim, no French incident handler. If the model returns something that can't be read as a `Category`, you get a typed error carrying the raw response, which beats a panic in a string splitter at three in the morning.

You might be feeling a very reasonable suspicion right now: *something* is writing a prompt. Something is parsing. Where did all that work go? It went into a layer you'll crack open in [Chapter 4](/docs/learn/what-the-model-sees), and you'll get to read the exact prompt your enum became. Trust, but verify. We'll verify.

One more thing you wrote without being told why: `init_tracing()?`. One line, first thing in `main`. Keep it there. Every run of every predictor is being quietly written down, and much later in this book that habit is going to pay for itself in a way that feels like cheating.

## The ceiling

Enjoy the win, but look at what you actually built: one enum classified one email.

A real front desk needs more from that same ticket. Is there an order ID buried in it? How angry is this customer (Herman's owner: moderately)? How urgent is it, and would you trust the model to rate its own confidence with a bare unchecked float? Can a contract carry a nested struct, an optional field, a value with *rules* attached?

That's not a bigger prompt. That's a richer contract.
