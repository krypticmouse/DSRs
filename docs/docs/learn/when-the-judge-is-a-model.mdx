Chapter 12 ended on an uncomfortable inventory: triage at 84% and climbing, replies ungraded and ungradeable. There is no `==` for warmth. No `assert` for "actually addressed the problem." The qualities customers experience most are precisely the ones your metric can't see.

Or, wait. Can't *see*, or can't *compute*? Because grading a reply is not mysterious. You do it every time you read one: does it name the real problem, is the tone right for a frightened starter-owner, is it concrete, did it avoid promising a refund. That's reading comprehension plus a rubric. And you happen to have a machine for reading comprehension; you've been paying it by the token for twelve chapters.

The move is almost cheeky: make the judge a model. But make it a *DSRs* judge, which means: typed, contracted, and honest about being one more signature.

## The judge is just another contract

```rust
/// Grade a customer support reply. Score 0.0 to 1.0.
/// Judge: does it address the customer's actual problem, is the tone
/// right for their mood, is it concrete, does it avoid promising refunds?
/// Critique the weakest aspect in two sentences.
#[derive(Signature, Clone, Debug)]
struct JudgeReply {
    #[input]
    ticket: String,
    #[input]
    reply: String,

    #[output]
    #[check("this >= 0.0 and this <= 1.0", label = "score_range")]
    score: f64,

    /// What is weakest about this reply, concretely
    #[output]
    critique: String,
}
```

Every trick from Act I reports for duty: the rubric is a docstring, the score wears the Chapter 2 range-check, the critique is a typed output. Wire it into a metric, and notice the Chapter 11 promissory note coming due, `Eval` was always built to carry words as well as a number:

```rust
struct ReplyQuality {
    judge: Predict<JudgeReply>, // pin this to a strong model
}

impl TypedMetric<DraftReply, FrontDesk> for ReplyQuality {
    async fn evaluate(
        &self,
        example: &Example<DraftReply>,
        prediction: &Predicted<DraftReplyOutput>,
        _trace: Option<&Trace>,
    ) -> anyhow::Result<Eval> {
        let verdict = self.judge.call(JudgeReplyInput {
            ticket: example.input.ticket.clone(),
            reply: prediction.reply.clone(),
        }).await?;

        Ok(Eval::with_feedback(verdict.score, verdict.critique.clone()))
    }
}
```

The desk writes. The judge reads. The metric returns a score *and a reason*.

## Why the reason changes everything

Here's the difference the feedback string makes, and it's the difference between two children's games.

A score-only optimizer plays Marco Polo. Try a candidate: 0.62. Try another: 0.58. Colder. Another: 0.66. Warmer. It gropes toward quality through numbers that say *how wrong* but never *what kind of wrong*.

**GEPA** plays with its eyes open. It's a reflective, evolutionary optimizer built to consume exactly what your judge now produces. Each generation, it takes candidates and their *critiques*, hands them to a reflection model, and asks the only question that matters: given what the judge said, what should change? The critiques are specific ("opens with policy boilerplate before acknowledging the customer's fear"), so the mutations are specific (an instruction gaining the line *open by naming the customer's problem in their own words*). Then the children are scored, the strong survive, and the loop turns.

Point it at the drafter overnight:

```text
gen 3  candidate 9b21: score 0.64
       critique: "correct information, but reads like a form letter;
       the customer's panic about Herman is never acknowledged"
gen 4  candidate a17f (mutated from 9b21): score 0.79
       instruction diff: + "If the customer names something they care
       about, acknowledge it by name in the first sentence."
```

Read that twice, because it's the thesis of this whole book cashing out. The judge's *words* became an *edit* to a named dial, and the edit is sitting in a diff you can review. Herman got a clause in your prompt, and you can point to the critique that put it there.

## The frontier

One more idea rides in with GEPA, and it fixes a lie that single numbers tell.

Push warmth and replies get longer. Push brevity and they cool. Which candidate is "best" depends on weights you'd be inventing at 6pm again. So GEPA doesn't keep one winner; it keeps the **Pareto frontier**: every candidate not beaten on *all* axes at once.

```text
frontier after 6 generations:
  c41  warmth 0.91  brevity 0.55   the empathy specialist
  c58  warmth 0.82  brevity 0.78   the all-rounder
  c62  warmth 0.66  brevity 0.93   the terse professional
```

Three legitimate desks, three honest trade-offs, and *you* choose per deployment instead of letting an averaged scalar choose invisibly. The e-commerce webhook might want `c62`; the community inbox wants `c41`.

## Keeping the judge honest

A judge that's a model inherits model problems, so the craft here is real. It costs a call per graded reply, so evaluate on minibatches and let [replay](/docs/learn/the-expedition-log) keep unchanged steps free. It has tastes, so anchor it: mix crisp checks you can compute (did the reply mention the order status when one existed? did it stay under length?) with the judged qualities, a hybrid metric, half arithmetic, half rubric. For the common shapes, classification agreement, string similarity, multi-objective mixes, retrieval and code pipelines, the [feedback helpers](/docs/reference/evaluate) will hand you well-formed score-plus-feedback without hand-rolling. And every judge verdict is itself traced, so you can audit the auditor: when a score looks weird, read the judge's span like any other step.

Turtles, yes. But *inspectable* turtles, all the way down.

## The ceiling

Look at what's on your laptop tonight. Triage at 84% by an optimizer that mined your own logs for demos. A drafter whose warmth was evolved under a reading judge, with Herman's clause in the diff. A frontier of three desks, each with a number and a pedigree.

And all of it exists as *tracing paper*: overlays and program files in a working directory, plus source on a branch. Meanwhile the actual tickets are landing in the actual inbox, answered by whatever you deployed weeks ago, the desk equivalent of a flip phone.
