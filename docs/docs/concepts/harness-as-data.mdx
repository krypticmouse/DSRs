DSRs starts from one belief. The model is rarely the problem. The setup around the model usually is.

Think about what sits around every model call. The instructions you wrote. The examples you picked. The tools you offered. The order of the steps. The wiring between them. That whole setup is what DSRs calls a **harness**. When you write one in DSRs, it is also called a program. Same thing, two names.

When a pipeline fails, people often blame the model. But given a good enough harness, a capable model can do almost anything. The hard part is finding the right harness. So DSRs is built to do one job well: make harnesses easy to build, easy to inspect, and possible to improve automatically.

## The big move: your program is also data

Here is the idea the whole project rests on. In DSRs, your program is not only code that runs. It is also a piece of data you can look at.

A useful picture is sheet music. A live performance happens once and is gone. Sheet music is the same song, but written down. You can read it, copy it, mark it up, hand it to another band, and compare two versions note by note. DSRs wants every harness to have its sheet music form.

Concretely, a DSRs program can be printed to a plain text file (a `.dsrs` file). That file holds the full picture: every step, every instruction, every tool, and how they connect.

## Why data beats code here

Code that only runs is a black box. Data opens the box. Once your program is data, you get things code alone can never give you:

- **You can diff it.** Two versions of a harness become two text files. You can see exactly what changed, line by line.
- **You can version it.** Check the file into git. Roll back a bad change. Review a good one.
- **A model can write one.** The text form is small and simple on purpose, so an LLM can generate a whole harness as easily as it writes a paragraph.
- **An optimizer can improve it.** A tool can rewrite an instruction, swap an example, or restructure a step, all without recompiling anything.
- **A server can run it.** Hand the file to a host and it can serve the program as is. That is what [compilation](/docs/concepts/compilation) means in DSRs.

## Every knob has a name and an address

There is one more piece, and it is what makes automatic improvement possible.

In a DSRs program, every part you might want to change has a name. Each instruction. Each set of examples. Each tool description. Each of these is a named parameter with its own address inside the program.

Why does this matter? An optimizer works like an editor with a red pen. An editor cannot fix "the writing" as one blob. They fix line four of page two. In the same way, an optimizer needs to point at one exact knob, try a new value for it, and measure the result. Named addresses make that pointing possible. Without them, improvement is guesswork. With them, it is a search.

This also keeps improvement safe. A candidate change in DSRs is just a small overlay: a list of addresses and new values, laid on top of the fixed program. The program itself is never mutated. Trying ten candidates means ten cheap overlays, not ten copies of your code.

## What this looks like in practice

You do not have to write data by hand. You write normal Rust, and DSRs produces the data form for you. There are a few ways to write, described in [Three Lanes](/docs/concepts/three-lanes). Some real logic can never be described as data, and DSRs is honest about that too, with a concept called [holes](/docs/concepts/holes).

Runs of a program also become data, as [traces](/docs/concepts/traces-and-replay), so the same idea applies twice: the program is data you can improve, and each run is data you can replay. And because programs can carry code and call tools, the data form also declares what the program is allowed to touch, through [capabilities](/docs/concepts/capabilities).

One belief, carried all the way through: if you can hold it in your hand, you can understand it, and you can make it better.
