There are three ways to write a harness with DSRs. They are not rivals. They work together, and you can mix them in one project. The difference between them is how much of your program the system can see.

Remember the core idea from [The Harness as Data](/docs/concepts/harness-as-data): a program is most useful when the system can hold it as data. Each lane trades a little of that visibility for a different kind of comfort.

## Lane one: structs

The classic way. You define a struct, implement a `forward` method, and write whatever Rust you like inside it.

This gives you the most control. Any logic, any state, any library. But the body of your method is just compiled code. The system can run it and watch it run, but it cannot read it. It sees a closed door with a label on it.

## Lane two: function calls with fx

The quick way. You call predictors as plain functions, with named slots for their instructions and examples. No struct, no ceremony. Good for scripts, experiments, and small tasks.

The system knows each call site by name, so it can tune the prompts. But the glue between the calls is still your own opaque code.

## Lane three: `#[module]`

The recommended way for pipelines. You write a normal async function and put `#[module]` on it. You still write plain Rust: let bindings, awaits, an ordinary return.

The trick is that the macro reads your function once and produces two things from that single read: the runnable function, and a full data picture of it. Your steps, their order, and the wiring between them all land in the program artifact. This is how a Rust harness gets its sheet music. The details of how that works live in [Compilation](/docs/concepts/compilation).

## What each lane gives you

| | Structs | fx calls | `#[module]` |
|---|---|---|---|
| Run it | Yes | Yes | Yes |
| Trace its runs | Yes | Yes | Yes |
| Tune its prompts | Yes | Yes | Yes |
| Full control of the code | Yes | Some | Some |
| Print it as a `.dsrs` file | No | No | Yes |
| Serve it from a file | No | No | Yes |
| Restructure it with an optimizer | No | No | Yes |

## The honest rule

The rule underneath the table is simple. If the system cannot see your code as data, it can still run it, trace it, and tune its prompts. But it cannot print it, serve it from a file, or restructure it.

This is not a punishment. It is just physics. An optimizer cannot rearrange steps it cannot see. A server cannot load a function body from a file, because the body is not in any file it can read.

So the advice is gentle. Use structs when you need total control. Use fx when you want something quick. Reach for `#[module]` when you are building a pipeline you may want to inspect, ship, or improve later. And when part of your `#[module]` function is logic no framework could describe, DSRs does not reject it. It wraps it and names it, as a [hole](/docs/concepts/holes).
