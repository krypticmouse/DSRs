Every real program has a bit of logic that no framework can describe. A custom filter. A scoring rule. A line of glue that only makes sense in your codebase. Most frameworks pretend this does not happen, and the pretending fails in one of two ways: either the framework forbids your logic, or it silently loses track of it.

DSRs does neither. It gives that logic a name: a **hole**.

## A typed black box

A hole is a black box with labeled sockets. When part of your `#[module]` function cannot be turned into data (see [Compilation](/docs/concepts/compilation)), DSRs wraps it as a hole in the program picture. The system knows exactly what goes in and exactly what comes out, because the types come from your Rust code. It just does not know what happens inside.

That is a real and useful contract. Think of a kitchen appliance. You do not know the circuitry inside a blender, but you know what you put in the jar and what you pour out. That is enough to plan a whole recipe around it. A hole lets the rest of your program be planned, checked, and improved around a part that stays private.

## Two kinds of holes

There are two kinds, and the difference is about where they can run.

**Sandboxed holes** are little JavaScript programs carried inside the program file itself. They run in a sandbox, so they can be executed safely by any host that loads the file. A program made only of steps and sandboxed holes is fully portable. The file is the whole program, and it runs anywhere.

**Native holes** are Rust code. They are fast, but they cannot travel. Compiled Rust cannot be put inside a text file, so the program file marks the hole as `extern` and records a fingerprint of the source it was made from. Only a binary that actually contains that code can run the program, and the fingerprint lets a host check it has the right version, not just something with the same name.

This split gives programs an honest portability story. A file with only sandboxed holes runs anywhere. A file with a native hole runs only next to the binary that defined it. The file itself tells you which one you have.

## Opacity is always reported

Holes are legitimate, but they have a cost, and DSRs makes the cost visible.

The parts the system cannot see are the parts it cannot improve. An optimizer can rewrite an instruction, because the instruction is data with an address, as described in [The Harness as Data](/docs/concepts/harness-as-data). It cannot rewrite the inside of a hole, because there is nothing there to read. Every hole is a small blind spot on the optimization surface.

So every `#[module]` reports its holes: which parts became holes, what they look like, and why they could not be described. Nothing becomes opaque in silence. If you want a hard guarantee, you can ask the macro to refuse holes entirely, and any unmappable code becomes a build error instead.

## Fewer and smaller is better

The practical guidance falls out naturally. Holes are fine. Big holes are expensive. Every step you move out of a hole and into the visible program is a step an optimizer can tune and any host can run. Fewer and smaller holes mean more of your program can be improved and shipped.

One last note: because holes are code, they are also subject to the permission system. A hole can only touch what it declares, and never more than the program allows. That story is told in [Capabilities](/docs/concepts/capabilities).
